# v1.0 开发验收：待支付订单继续、超时与取消

仍为 `1.0.0-dev`，不发布正式版本。商店负责订单、支付、库存和退款的真实状态，Bot 只提供入口和防重复提交保护。

## 继续支付

从“我的订单”打开待支付订单，点击“继续支付”：先用当前 Telegram 用户读取订单，再调用上游只读 `GET /payments/latest?channel_user_id=...&order_id=...`。接口证据见固定官方 v1.5.0 的[路由](https://github.com/dujiao-next/dujiao-next/blob/41b86260dc9a60269526057eed8d915844ceb3a3/internal/modules/channelapi/transport/http/routes.go)和[支付处理器](https://github.com/dujiao-next/dujiao-next/blob/41b86260dc9a60269526057eed8d915844ceb3a3/internal/modules/channelapi/transport/http/channel_order_payment.go)。

- 存在有效的待支付记录时，复用原链接、实付金额、链上收款信息和支付记录 ID，不调用创建支付。Bot 重启后也从商店恢复，不把支付链接缓存在 Redis。
- 只有明确 `404 payment_not_found`、订单仍可支付且没有未确认请求时才展示渠道选择；500、鉴权失败、未知响应或错误订单 ID 都不是“没有支付”的证据，不据此自动创建新单。
- 选择渠道时生成十分钟有效、绑定用户/订单/消息的一次性令牌，保存允许渠道 ID。实际点击前重新读订单与最新支付；有原支付则继续使用，没有才允许原子领取一次创建请求。旧版无令牌按钮只打开新的支付选择，不直接提交。
- 有效原支付存在时不主动切换渠道，也不尝试用余额再支付一次；上游渠道接口没有提供独立取消支付单的动作。不想继续时可在确认尚未付款后取消订单，或者等待原支付失效再按新提示明确选择。余额不足会在请求扣款前给出提示，仍需以商店最终扣款校验为准。
- 正常创建支付后自动展示一次二维码；恢复原支付不反复推送二维码，可按需点击“显示二维码”。明确点击显示可能产生一条新的二维码消息，不承诺二维码消息 exactly-once；它不会创建新支付记录。
- 重复按钮、网络断开、上游 `payment_create_failed`（即使 HTTP 400）、响应丢失或完成状态保存失败不自动重发资金请求。重新核对读到有效原支付可以恢复；仍无法确认时请联系商家，不能凭“暂未查到”解除保护。

## 超时提示

| 场景 | Bot 行为 |
| --- | --- |
| 订单支付时限已到、商店还返回待支付 | 列表及详情明确提示到期，不再提供继续支付；可刷新核对或显式取消，不把本地时间当作商店已取消状态 |
| 原支付记录失效、订单仍在有效期 | 不使用旧链接，展示重新选择方式的入口，并提醒已付款用户先核对账户；不自动建支付 |
| 自动查询到截止时间或运行十五分钟上限 | 清理该轮二维码，提示“自动查询已暂停，不代表付款失败”，仍由商店查询结果决定状态 |

详情显示本次刷新时剩余的大约分钟数及明确的 UTC 截止时间，不提供会自行跳动的倒计时。轮询使用订单/支付截止中更早的有效时间，已在过去的截止时间不会被延长十五分钟。缺失或无效的截止值不伪造精确的过期时间，自动查询仍有十五分钟上限。

## 取消订单

点击“取消订单”先重新读取归属与待支付状态，确认页显示订单号、金额及“已付款不要取消”的提醒；“暂不取消，继续支付”为首要操作。确认五分钟有效并绑定该消息；返回后旧确认立即失效，空令牌、串消息、串用户、群聊和过期确认都不能提交。

最终确认前再次查询订单，并以独立 Redis CAS 抢占取消请求；支付创建与取消互斥。已支付/已关闭时仅展示当前订单，不再发送取消。取消成功停止该订单的轮询、清理二维码，提醒原支付链接勿再使用。重复确认和重启后旧确认不会重新提交。

取消结果不明会保留保护并引导重新查询，不因时间过去自动补发。取消不是退款，也不能阻止用户向已经关闭的外部收款地址转账；若已付款或之后到账，必须由商店和支付提供方核对处理，Bot 不自行退款或重新下单。支付回调与取消的最终并发冲突仍由商店事务保证。

## 持久化和回滚边界

独立 `checkout:v1` 命名空间保存七天、上限 10000 个用户/订单资源：仅哈希键、UI 令牌/消息/期限、渠道数字 ID、支付记录数字 ID及支付/取消状态；不保存支付链接、二维码、地址或用户输入。与会话草稿、提现、通知和 TXT 回执格式分开，取消输入或导航不会清除未确认请求。

Redis CAS 闭包只执行一次；失败、冲突、容量满、损坏记录、epoch 丢失和提交确认丢失均不授权资金请求，不回退内存。真实 AOF 重启检查包括未确认支付和取消状态。内存模式只提供本进程保护；七天到期、清空/回滚 Redis 或退回不识别此保护的旧 Bot 都不具备同样保证。保持稳定命名空间、持久化和 `noeviction`，不要清理 Redis 来解锁；有未确认操作时应先核对商店及支付账户，再评估降级。此功能不承诺所有外部支付环境的 exactly-once。

## 自动验收

```sh
make verify
make telegram-e2e
```

- 单元/竞态：原记录复用、并发创建、余额不足不扣款、余额支付旧确认不重复扣款、查询失败不猜测、响应丢失（可查/暂不可查）、私聊隔离、篡改渠道、过期选择、返回/空令牌/旧确认、付款后取消、未知取消、领取/完成确认丢失，以及轮询时限和暂停提示。
- Redis：跨客户端单次领取、导航与进程重建保留保护、返回数据隔离、损坏/容量/epoch/CAS 冲突与响应丢失；真实 AOF 两阶段测试保存未确认支付和取消。
- SQLite/PostgreSQL：真实官方 v1.5.0、真实 Bot/Redis、隔离 Telegram 和支付 peer。通过返回按钮下单付款，重复选择、Bot 重启后继续支付仍是一条原支付记录及相同链接；另一用户读取最新支付必须得到明确归属拒绝。取消返回后旧确认失效，最终取消及重复/重启旧确认后仍只有一张订单、一条提供方记录、钱包不变。原正常支付/充值/人工交付链路同时回归。

2026-10-20 本地 Docker Desktop ARM64：三轮全量竞态、静态/依赖检查与构建，以及两种数据库的恢复/取消专项和正常支付/充值/交付回归通过。AMD64、完整升级/自动交付组合及压力结果以对应提交 CI 为准；合成支付不代表真人 Telegram 客户端和真实支付提供方已验收。
