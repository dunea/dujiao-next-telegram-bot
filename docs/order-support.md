# v1.0 开发验收：订单售后与客服

仍为 `1.0.0-dev`，不自动发消息、不创建工单、不申请或执行退款。售后规则与处理结果由商家决定。

## 用户入口

订单详情增加“售后 / 客服”，普通 Telegram 客服账号同时提供“带订单号联系客服”的直达按钮。售后页可选支付未到账、交付或使用问题、退款咨询、订单咨询；切换后生成只含完整订单号和问题类型的消息，支持复制售后消息与单独复制订单号。刷新和返回订单详情保留原订单筛选/页码。

售后页使用紧凑分组：客服主入口整行、复制操作两列、问题短标签两列，刷新和返回订单详情并排；完整问题描述仍保留在咨询草稿中，不因缩短按钮而改变咨询类型或自动发送。带客服入口的常见页面由六行收紧为五行。

待支付页提醒先刷新、不要重复付款或取消；已支付/处理中提示等待交付，部分交付不冒充全部完成；交付后提示描述错误而不发送完整卡密；关闭/退款订单明确由商家核对，不把咨询按钮当作退款申请。

## 配置与链接兼容

复用 Dujiao-Next 的 Telegram Bot 配置 `basic.support_url`，不增加必填环境变量、不硬编码收件人。首页和帮助页使用同一客服配置。正常运行约每五分钟刷新配置；修改后可等待配置刷新或只重启 Bot，不需要重建商店或 Redis。

- 普通账号：推荐 `https://t.me/your_support`，也支持 `@your_support`、`t.me/your_support`、`telegram.me` / `telegram.dog` 别名以及 `tg://resolve?domain=your_support`。规范化为 HTTPS `t.me` 链接，仅对普通用户名链接设置 `text` 草稿参数，并去除会打开资料页的 `profile`。不继承原有 `text` 中的任意内容。
- 客服机器人（用户名以 `bot` 结尾）、有 `start`/其他路由参数的链接、Business `t.me/m/slug`：保留原来的目的地与参数，不擅自编造客服机器人协议或覆盖 Business 的服务器端消息。
- HTTP/HTTPS 客服网站：原链接不追加任何订单参数，先复制消息再打开。不会把订单号发给链接跳转器、分享选择器或不明第三方查询接口；不支持通用 `{order_no}` 模板替换。
- 空配置、格式错误、凭证 URL、非 HTTP/HTTPS 协议（除明确的 `tg://resolve` 转换）、Telegram 代理/分享/登录等系统动作：不生成客服 URL。售后入口与复制功能仍可用，提示通过商家原有渠道联系，不指定假收件人。

普通用户名链接的草稿行为依据 [Telegram 官方深链接说明](https://core.telegram.org/api/links#public-username-links)：仅在目标聊天允许输入时预填，仍需用户确认并发送。不能仅凭 URL 离线确认目标是私人账号、群组或是否存在，商家应配置正确客服账号，用户打开后核对收件人；Bot 不做外部账号探测、不自动发给客服。无法预填的客户端可使用复制回退。

复制按钮使用 [Telegram CopyTextButton](https://core.telegram.org/bots/api#copytextbutton)，文本限制为 1–256 字符。消息只含最多 100 个 ASCII 字符的完整订单号及短话术，三种语言均有长度回归；旧客户端不支持按钮时，可长按页面中可见的消息复制。没有有效完整订单号时不截断后生成错误咨询编号，提示刷新或核对商家。

## 隔离与边界

售后回调只接受当前用户私聊，始终按当前 Telegram 用户重新调用归属受限的订单接口，检查返回 ID；他人订单、群聊、无效数字 ID 和不匹配响应不生成订单上下文。生成内容不含商品标题、卡密、购买表单、金额、支付链接/凭证、用户 ID 或其他个人资料；不写入日志或新的 Redis 草稿，不打断现有购买资料，不删除提现/结账/TXT 保护。

直接 URL 与复制按钮是当次生成的静态内容，不能在点击时重新读取商店；修改配置或订单状态不会自动改写历史消息。售后页的刷新/旧问题回调会重新查订单与当前配置。只向订单所属私聊生成上下文，不承诺阻止用户自行转发、截图或分享订单号；商家、Telegram 和用户选定的客服渠道仍可能保留记录。

## 自动验收

```sh
make verify
make telegram-e2e
```

- 链接测试：普通账号草稿、编码/覆盖旧文本、去除 profile、机器人 start/Business/网站回退、错误参数/协议/凭证/系统动作拒绝。
- SDK/竞态：订单详情直达、三语言/四种话术长度、复制按钮唯一动作、私聊与归属、无效回调、返回 ID 不匹配、旧按钮读取新状态/新配置、草稿与资金保护保留、不写账务、不记录原文。
- `TestTelegramOrderSupport`：固定官方 v1.5.0，SQLite/PostgreSQL 独立栈，正常管理 API 只修改客服字段并核对其他配置不变；真实 Bot 按订单号打开详情，检查正确收件人/订单/问题、SDK 复制按钮、返回上下文、重启后旧回调、网站与未配置回退。最后订单仍待支付，网关、余额与流水没有变化。

自动化不打开外部客服链接，不向真实客服发消息。真实 Telegram 客户端能否预填、复制和顺畅返回，仍需人工体验；通过协议 peer 不等于全部客户端或商家售后流程已验收。

2026-10-20 本地 Docker Desktop ARM64：三轮全量竞态、静态/依赖检查与构建，以及 SQLite/PostgreSQL 的售后专项通过。AMD64、完整升级/支付/交付组合、Redis AOF 与压力检查以对应提交 CI 为准，不将本地专项外推为全部验收通过。
