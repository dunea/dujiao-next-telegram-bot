# v1.0 开发验收：持续压力与自动卡密

本批仍为 `1.0.0-dev`，不发布正式版本、不更新现有演示 Bot。复用[回调故障与全链路验收](callbacks-and-e2e.md)的隔离策略：固定官方 Dujiao-Next v1.5.0、真实 Bot/Redis/队列，Telegram API 与 Epay v1 使用本地协议 peer。两种数据库独立运行，不连接真实商户、真实支付服务或公网 Telegram。

## 执行

```bash
make telegram-e2e                      # 人工交付 + 自动卡密 + 连续重启，两种数据库
make soak-test                         # SQLite、PostgreSQL 各持续 5 分钟，再收尾核验
DUJIAO_REAL_DB=postgres make soak-test
DUJIAO_SOAK_DURATION=15m make soak-test # 每种数据库独立 15 分钟
```

时长允许 `1m` 至 `30m`，默认每种数据库 `5m`；启动/构建及结束后的通知补投不计入持续阶段，所以实际命令耗时更长。时长和数据库类型先校验，再创建容器。需要 Go、本机 Unix-socket Docker daemon，SQLite 路径另需 `sqlite3`。不读取 `.env`，不接受外部商店地址、目标 URL、Bot Token、数据库 DSN 或已有卷覆盖；测试只使用新建的随机网络、容器和合成凭证。

CI 的两种数据库任务依次执行三个版本升级链、人工/自动交付 E2E，以及各 `90s` 的持续负载冒烟。不能把 CI 的 90 秒记录说成五分钟或长时间生产稳定性证明；更长本机运行使用上述参数。CI 仅上传脱敏测试输出，不上传数据库、卡密、凭证、peer 状态或后台/审计全文。

## 自动卡密全链路

通过正常官方后台 API 创建独立自动交付商品、默认 SKU 和三张合成卡密；测试不直接改库存 SQL、不调用人工履约来代替自动任务。通过实际 Telegram `getUpdates`、SDK 和返回按钮，完成两笔在线订单，购买数量依次为 `2`、`1`：

- 下单时验证 `available → reserved`，付款前不能在订单详情读到卡密。另一已绑定的合成用户读取该订单必须得到官方 `404 order_not_found`，不能把网络错误当作越权拒绝通过。
- 错误支付签名保持待支付、无交付内容；有效 Epay 回调触发真实支付和官方自动履约。订单完成、到账货款分别为 `6.50` / `3.25 CNY`，钱包不扣款。
- 官方交付内容恰好含购买数量的已导入卡密，无单内重复、无跨订单重复；卡密 `used` 关联本订单/子订单，库存计数从三张逐步降至零，不遗留预占。
- 同一笔支付成功回调再重复两次，卡密 ID/状态/归属、交付内容及订单完成状态不变。最终每笔订单只有一条交付通知。
- 从 Telegram 我的订单读取完整交付内容，包含 `<`、`&`、`>` 的卡密必须 HTML 转义；不显示仍未分配或另一订单的卡密。Bot 重启后仍可读取第一次交付。
- 售罄后商品显示售罄按钮，不再提供数量/购买入口；余额、钱包流水均保持零，审计不含卡密全文。

该路径针对固定官方版本的[自动履约服务](https://github.com/dujiao-next/dujiao-next/blob/41b86260dc9a60269526057eed8d915844ceb3a3/internal/modules/fulfillment/application/service.go)及其真实后台接口；不等于上游分销采购、混合购物车、退款回收、所有自定义模板或长卡密附件发送均已覆盖。

## 持续负载模型

负载进程在隔离网络的 peer 容器内发请求，避免把每次请求的 `docker exec nc` 开销算作 Bot 吞吐。目标固定为 `http://bot:8444` 和 `http://peer:8080`，测试二进制不接受任意网络目标，不进入正式 Bot 镜像或发布包。

- 固定目标 `100 请求/秒`，16 个 worker、16 个待处理任务的有界队列；约 80% 健康检查、20% 三类有效签名通知回调，HTTP 连接复用、单请求五秒截止，不积累无界延迟样本。
- 保持默认用户/来源限额，单个合成用户的高频回调会被正常限流。`Accepted` 包含健康检查和已确认/已去重回调；`Limited` 单独统计，绝不把“100 请求/秒”说成“100 条通知/秒”或真实 Telegram 发送能力。
- 三个阶段使用不同资源集合；在三分之一、三分之二处各注入一次 Telegram `429`、`500`，既有请求持续运行。peer 必须实际消费这两次故障，不能只设置故障却没有发消息。
- 每十秒输出一个窗口，记录请求、健康检查、接受、限流、临时重试、非预期错误和健康/回调 P99；延迟采用固定 25ms 桶的上界近似，不保存逐请求正文/令牌或无限增长的样本数组。
- 持续阶段后逐个补投 96 个不同合成资源，再发一个新的恢复探针。最终 97 条有效通知必须各一条，无重复，并确认 Telegram `/wallet` 仍可响应、商店订单/余额/钱包流水都未改变。

这些回调只测试 Bot 的通知入口和 Redis/SDK 投递路径，**不是 100 TPS 商店支付交易测试**。不会通过压测发起真实下单、充值或提现；真实自动履约由前一节单独验证。

## 失败门槛与资源预算

| 指标 | 必须满足 |
| --- | --- |
| 已完成请求 | 持续阶段达到目标请求量的至少 90% |
| 非预期错误 / 队列丢弃 | 均为零；健康失败、网络错误、鉴权失败、损坏响应也算错误 |
| 限流 | 必须实际发生，且是明确 `rate_limited` + 合法 `Retry-After`，不接受任意 429/503 |
| 临时重试 | 仅明确的投递未决/SDK 失败，合计不超过 16；最终必须全部恢复，且两次故障各实际发生一次 |
| 存储/一般服务错误 | `limiter_unavailable`、`receipt_unavailable`、未知 5xx 均失败，不掩盖成预期限流 |
| P99 | 健康 ≤1500ms；回调（包含拒绝响应）≤2500ms |
| Bot 资源 | 每 15 秒及结束时采样；RSS ≤128MiB、相对启动增长 ≤64MiB、线程 ≤128 |
| Redis 资源 | `used_memory` 相对启动增长 ≤16MiB |
| 业务与恢复 | 97 条各一次、钱包/流水/订单未变、最终健康及 Telegram 查询通过 |

RSS 与线程从本次 Bot 的 `/proc/1/status` 读取，Redis 从本次实例 `INFO memory` 读取；缺失指标必须失败。预算是当前测试规模下的回归门槛，不是生产容量建议，也不证明没有内存泄漏。当前没有测最大承载、生产数据库支付 TPS、CPU 预算、全天稳定性或回执 10000 容量满时的实栈吞吐；回执容量边界另有离线回归。Telegram 已接收但响应丢失时仍可能重复通知的边界保持不变。

开发版已拆分原先含糊的 `delivery_unavailable`：只有明确的 `delivery_busy`（已读取到未决租约/冷却）可进入有严格次数上限的临时重试，不能计为成功或正常限流；最终还必须逐个资源补投确认并检查业务/资源状态。所有 `receipt_unavailable`（包括读取/写入故障、CAS 冲突）、旧含糊状态和未知响应直接失败。阶段和日志原因见[重启回调诊断](callbacks-and-e2e.md#重启回调专项与脱敏诊断)。

清理沿用随机 owner 标签核验，只移除本次容器/网络/镜像和成功测试的 PostgreSQL 卷；失败数据及私有日志保留在输出中的临时目录，不操作演示或已有数据卷。
