# Dujiao-Next 兼容性矩阵与升级测试

核对日期：2026-10-20。Bot 开发版本：`1.0.0-dev`，已发布稳定版：`v0.4.0`。

本项目使用 `/api/v1/channel/*`，不是前台 `/api/v1/*` 或站间 `/api/v1/upstream/*`。例如前台订单改用 `order_no`，不代表渠道 API 的数字订单 ID 已消失；已核对的渠道路由仍有 `/orders/:id`。不根据商店界面、`config_version` 或主版本号猜测 API 能力。

## 证据级别

- **源码核对**：固定官方提交，复核八个关键协议文件的 SHA-256；不是运行真实后端。
- **协议契约测试**：根据已核对字段人工构造合成数据，测试本项目的签名、解码、错误处理和版本切换；不是官方响应录制，也不是三套真实商店端到端。
- **跨 Bot 版本存储测试**：真实 `v0.4.0` 源码写入隔离 Redis，当前代码读写，再由真实旧代码读取；不同于仅重连当前客户端。
- **真实实例/数据库升级**：本批尚未执行三个上游版本的真实实例、SQLite/PostgreSQL 迁移或商家支付闭环。矩阵不将它们标为已通过。

## 可重复执行的检查

```bash
make compatibility   # 本地合成协议、只读保护及诊断命令测试，含竞态检查
make upstream-audit  # 只从官方固定提交下载 24 个文件并核对哈希，不运行上游代码
```

普通单元测试不访问互联网。源码复核需连接 `raw.githubusercontent.com`；网络失败显示 `fetch_error`，哈希变化显示 `hash_mismatch`，两者均退出非零，不伪装成验证通过。固定提交校验保证本次证据可复现，不自动发现未来新版本，也不通过哈希证明全部运行行为一致。CI 已加入独立的源码证据检查任务。

合成协议覆盖字符串金额、推广最低提现金额的数字表示、分页、未知字段、数字订单路由、身份邀请码边界与不自动重试。故障测试区分 404/501、401/403、429、5xx、缺失成功字段、重定向和正文不可信；未知/损坏响应不会被标为读取通过。上游版本切换序列使用相同客户端和合成服务，未执行真实数据库迁移。

## 商店升级前后的只读诊断

使用测试环境的 Channel Key/Secret，注入进程环境（不自动加载 `.env`；不要把秘密写进命令行或提交到 Git）：

```bash
go run ./cmd/compatcheck
# 可选：只读取已有测试用户的钱包、流水和推广资料，不创建账号
go run ./cmd/compatcheck -user-id 123456789
# 当前开发版镜像也包含诊断工具，无需在宿主机安装 Go
docker compose exec -T bot /usr/local/bin/dujiao-compatcheck
```

该工具从 v1.0 开发分支开始加入，已发布的 v0.4.0 下载包/镜像没有它；不要因此修改旧版发布附件。

命令读取 `DUJIAO_BASE_URL`、`DUJIAO_CHANNEL_KEY`、`DUJIAO_CHANNEL_SECRET`，不读取 Bot Token 或 Redis 密钥。默认只检查配置、分类及充值渠道；显式给定用户 ID 后增加钱包/流水及推广查询。不要将生产用户的 ID 或诊断结果公开。

所有请求只允许 GET，传输层拦截 POST，并禁止跟随重定向，不会发送心跳、自动注册、兑换卡、下单、充值或申请提现。GET 不意味着上游绝不写入任何数据：上游鉴权会更新渠道 `last_used_at`，商店或代理也可能记录访问日志。地址应直接指向最终 Channel API 服务。

JSON 只含固定检查名、状态、HTTP 状态码与配置修订号，不含令牌、余额、收款信息、原始响应、服务器 URL 或任意错误全文。`upstream_version` 保持 `unknown`：当前渠道配置接口没有提供可靠的上游发行版本，`config_revision` 不能当作 Dujiao-Next 版本。

| 结果/退出码 | 含义 |
| --- | --- |
| `accepted` | 本次 GET 返回可解码的所需读取结构，不证明业务写入或支付已兼容 |
| `missing` | HTTP 404/501，可能是缺少路由，不据此猜测具体发行版 |
| `denied` | HTTP 401/403，先查凭证、权限或账号，不当作缺少功能 |
| `throttled` | HTTP 429，等待限流恢复，不自动重试或扩大额度 |
| `disabled_or_incomplete` | Bot 配置关闭或不完整，停止进一步诊断 |
| `invalid_response` / `unavailable` / `rejected` | 必需字段缺失、网络/解码/服务异常或其他拒绝，需要人工核对 |
| 退出 0 | 仅必需的配置/分类读取通过；可选项可能失败，必须检查每项结果；`write_checks` 始终为 `not_run` |
| 退出 1 | 必需读取失败，或源码复核失败；不要据此自动重提资金请求 |
| 退出 2 | 参数或环境配置不合法，输出省略敏感值 |

## Bot v0.4.0 → 当前开发版存储升级

先启动隔离测试 Redis（不需要真实 Telegram 凭证）：

```bash
docker compose -f compose.test.yml up -d --wait redis
BOT_UPGRADE_REDIS_URL=redis://127.0.0.1:16379 make upgrade-test
```

脚本只接受固定隔离端点 `127.0.0.1:16379`，不读取生产 `.env`。使用已发布 `v0.4.0` 的固定提交 `528b58b082ab91db8d69295015e1cb59c702f32c`，必要时从当前仓库 origin 获取该对象；归档到专用临时目录，不切换/覆盖用户工作区，不修改旧版代码。

1. 真实旧代码写入语言、提现确认草稿/结果不明保护、耗尽的限流额度、公告订阅/草稿/领取进度与冷却。
2. 当前代码读取并验证旧数据，保持未知提现保护，保留额度/授权/游标/冷却；公告暂停且不会调用发送；导航取消不会解除提现保护，并写出新的加密记录。
3. 真实旧代码读取新写入的同格式记录，再仅清理测试命名空间。

该测试覆盖 Redis v1 格式的前向读取及仍兼容的旧版读取，不是允许随意降级的承诺，更不代表上游商店数据库可逆迁移。脚本和旧版 fixture 只操作 `dujiao-bot:test-aof` 测试键；成功清理这些合成数据，失败时可保留测试键排查，不会清空数据库或删除持久卷。源码临时目录保留供复核。不要并发运行 AOF fixture 与此测试，它们共用固定测试命名空间。

`make acceptance` 和 CI 在 AOF 检查之后串行运行此升级测试；真实商店与演示 Bot 不参与。已有加密/损坏/未知版本拒绝测试继续有效，未知格式不能当作空会话初始化。

本批本地运行结果：三轮全量竞态、24 份源码哈希、上述真实旧/新存储往返及隔离 Docker 验收通过。隔离容器内八项只读检查均为 `accepted`，2000 次健康和 1000 次分散签名回调零失败；最近一轮 500 次单用户突发有 389 次预期 429（数量随额度恢复和并发时序略有变化）。该读检查针对 Mock API，不是表格中三个真实上游实例的运行证明。CI 状态以对应提交的 Actions 页面为准。

## 实际升级操作边界与待办

升级前停止 Bot，备份商店数据库、稳定加密密钥、Redis 一致性数据和审计卷。先在商家测试环境运行只读诊断，按上游对应版本的官方迁移规则升级，再用同一已有测试用户复查。不要改商店地址/Channel Key 来制造新命名空间，不要清空 Redis、恢复旧发送游标或换密钥绕过未决保护。

后续 v1.0 还需补齐：三个真实上游实例的认证读取与业务闭环、SQLite/PostgreSQL 数据迁移，以及商家支付回调验收。本批没有升级真实 Dujiao-Next 服务或操作真实资金；详细运维原则仍见 [RELEASE.md](../RELEASE.md)。
