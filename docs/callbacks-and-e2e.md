# v1.0 开发验收：支付回调故障与 Telegram 全链路

本批针对 `1.0.0-dev`，不是 v1.0 正式发布。官方后端固定为 Dujiao-Next `v1.5.0`，SQLite、PostgreSQL 各执行一遍；三个版本的逐版本升级另见[兼容性矩阵](compatibility.md)。这里使用真实 Bot 进程、真实官方商店及其任务队列，Telegram API 和 Epay v1 网关是隔离的协议模拟端点，**不是公网 Telegram 或商家真实支付渠道验收**。

## 复验入口

```bash
make verify                       # 离线故障回归、三轮竞态、静态检查及构建
make telegram-e2e                 # Docker Desktop：SQLite 和 PostgreSQL
DUJIAO_REAL_DB=sqlite make telegram-e2e
DUJIAO_REAL_DB=postgres make telegram-e2e
make real-upstream-test           # 三个官方版本的升级/恢复，不等同于 E2E
```

需要 Go、可用的本机 Unix socket Docker daemon；SQLite 路径还需 `sqlite3`。首次拉取固定镜像和构建测试镜像需要联网。CI 在两个真实上游数据库任务中串行执行升级链和 E2E；Go 任务另验证真实 Redis AOF 停启恢复。CI 仅上传测试摘要，不上传商店数据库、配置、后台日志、审计全文或 peer 状态文件。

## 全链路实际断言

注入 Telegram `getUpdates`，由真实 SDK 轮询和处理按钮，不直接调用交互处理函数：

1. `/start` → 新用户 → `/wallet` → 充值预设 `100.00 CNY` → 选择真实后台配置的 Epay 渠道；用户费率 `2.50%` 加固定费 `1.00`，界面和网关实付均为 `103.50`。
2. 网关回调错误签名、错误商户号、错误金额、未支付状态，均不增加余额或流水。正常回调到账 `100.00`，重复回调仍只有一条入账流水。
3. 首次充值通知注入 Telegram `429`，真实上游队列随后重试，最终收到一次成功通知，而非测试手动替代上游重试。
4. `/products` → 分类/商品/SKU → 购买及表单确认 → 在线支付 → 网关回调。错误回调保持待支付；成功及重复成功回调最终订单金额 `7.25`，不动用钱包余额。
5. 真实后台人工履约 → 官方交付回调 → Telegram 通知 → `/orders` 查看交付内容。对同一实际订单 ID 注入迟到支付通知、重复交付通知，不重复发送或倒退状态提示。
6. 重启 Bot 后仍能识别已发送通知；暂停本栈 Redis 时新回调 `503` 且不发送，恢复后业务可用。Telegram 轮询注入一次 `503` 后恢复，更新全部确认，无挂起更新。
7. 审计包含充值创建、订单创建/支付及支付/交付/充值回调事件；不出现本次 Token、渠道密钥、网关密钥、支付 URL 或交付全文。

E2E 配置支付渠道时，使用新测试数据库的合成管理员通过正常后台接口确认合规提示；不关闭上游合规中间件，不替真实商户作声明。模拟网关只接收合成订单，回调目的地固定为同一隔离网络的官方后端；模拟 Telegram 只允许固定合成收件人。没有实际充值、支付或打款。

## 回调故障矩阵与返回语义

| 情况 | 行为 |
| --- | --- |
| 签名错误、时间偏差超过五分钟、无效用户/业务字段、过大正文 | 拒绝，不发送、不保存投递回执 |
| 同用户同资源已有投递租约/冷却 | `503 delivery_busy` 和 `Retry-After`；正在处理者之外不发送 |
| 同一资源与事件的有效负载变化 | `409`；不覆盖旧回执、不发送；金额 `10` 与 `10.00` 归一为同值 |
| 已发送/明确永久拒收的重复通知 | `200`，不重复发送；同订单交付成功后的迟到支付通知也忽略 |
| Telegram `429`、`5xx`、超时或断连 | 持久冷却，`503` 和 `Retry-After`；等待上游重新投递 |
| Telegram 明确 `403` | 保存永久拒收并 `200`，避免对已屏蔽 Bot 的用户反复重试 |
| Redis 不可用、回执损坏/未知版本、容量满、原子写冲突或确认丢失 | `503 receipt_unavailable`，`stage=claim/finalize`；不回退内存，领取未确认时不发送，完成保存未确认时保留未决保护 |

重要修复：固定官方版本的[机器人回调消费者](https://github.com/dujiao-next/dujiao-next/blob/41b86260dc9a60269526057eed8d915844ceb3a3/internal/app/jobs/consumer/consumer_bot.go)将全部 HTTP `4xx` 视为结束、不重试。因此不能把 Telegram `429` 原样返回上游；已认证用户的临时业务限额也返回 `503`。HTTP 来源/全局防滥用限额仍为 `429`，不是可靠投递保障；部署时需按实际流量合理配置并监控。上游队列自行决定重试时机和次数，不保证严格遵循 `Retry-After`，Bot 不在 HTTP 请求内循环重发。

离线回归还覆盖每类事件 30 个并发重复请求、用户隔离、回执提交前/后响应丢失、领取租约到期、SDK 实际 HTTP 错误映射、日志隐私、Redis 清空/未知格式/容量上限，以及压测工具不把一般 `503` 误算成预期限流。

## 重启回调专项与脱敏诊断

`make telegram-e2e` 还包含 `TestTelegramCallbackRestart`：每种数据库使用独立新栈，先完成支付/交付/充值三类合成通知，再连续重启真实 Bot 五次。每轮三个回调必须立即返回 `200 duplicate_or_obsolete`，Redis 已完成回执前后逐字一致，通知总数仍为三；不对意外 `503` 自动重试，也不以通知已经可见代替回执已完成。此专项只测试通知，不发起真实或合成资金变动；实际账务闭环仍由前述全链路测试覆盖。

专项还对照同一测试镜像内 BusyBox 的传输行为：写完请求立即关闭 stdin 的旧方式会半关闭 TCP，使 Go HTTP 后端在仍可返回响应时取消请求上下文；固定等待探针返回 `canceled=true`。修正后保持 stdin 开放直到读完响应，实际测试隧道探针返回 `false`。这不是延长超时或忽略故障；另有真实 TCP 半关闭的单元测试。首次新增专项在旧隧道下捕获 `notify_failed`，模拟 Telegram 未收到消息，说明测试传输可以制造真实业务失败；仅凭历史缺失的正文不能认定过去那一次一定属于此路径。

开发版不再使用含义不清的 `delivery_unavailable`。状态区分如下：

| 响应 | 判读 |
| --- | --- |
| `503 delivery_busy` | 读到了有效的处理中租约或重试冷却；等待上游重投，不等于存储失败 |
| `503 receipt_unavailable`, `stage=claim` | 领取/读取回执未获确认，本次不发送 |
| `503 receipt_unavailable`, `stage=finalize` | 投递后保存未获确认，可能已经送达；保留保护，不手动重放资金操作 |
| `503 limiter_unavailable` / `rate_limited` | 限流存储不可用 / 额度拒绝，不与回执原因混淆 |
| `503 notify_failed` / `telegram_rate_limited` | 通知调用失败 / Telegram 明确要求冷却 |

存储故障日志 `callback unavailable` 只包含固定事件名、阶段、请求上下文状态及原因白名单：`read_failed`、`epoch_mismatch`、`invalid_receipt`、`expired_receipt`、`write_failed`、`cas_conflict`、`capacity_exhausted`，无法分类为 `unknown`。不记录 Redis 原始错误、地址、键、领取令牌、通知正文或凭证。按阶段/原因/上下文组合每分钟最多一条，不能把日志条数当作故障总量；请求取消后仍保留本地采样诊断，不脱离请求重发网络操作。`write_failed` 也可能是提交成功但确认丢失，不能据此认定未写入。

压力工具只把明确的 `delivery_busy` 和通知临时故障纳入有界重试预算，所有 `receipt_unavailable`（包括 CAS 冲突）、旧的含糊状态及其他存储失败均判非预期失败。E2E 失败时只在私有临时目录保存有界响应正文，公共输出只显示白名单原因/阶段；不会打印任意服务端正文。

曾出现的单次重启后 `503` 未保留正文，目前尚不能反推其唯一根因。测试隧道缺陷已用对照复现并修正；上述分类和专项继续用于取证，不代表已证明该历史故障的具体来源。

2026-10-20 本地 Linux ARM64 复验：SQLite/PostgreSQL 的对照、各五次重启、人工/自动交付全链路均通过；三版本双数据库升级恢复、三轮全量竞态/静态/构建通过。两条 `90s` 持续负载分别完成 8,998/8,985 次请求，非预期错误和丢弃均为零、97 条通知各一次、账目不变。这是新增诊断语义下的短期回归，不替代前述真实渠道或长时间容量验收；AMD64 结果看对应提交 CI。

## 持久化与保证边界

- 新的通知回执与会话/提现/公告记录分开，不改变旧格式。启用 Redis 时使用同一商店命名空间及数据集 epoch，原子 CAS 单次提交，不自动重放修改函数；保留 AOF、稳定配置及密钥。真实 AOF 重启验证 `sent`、`posting`、`retry` 与冷却保留。
- 每个用户/业务资源从首次领取起保存七天，最多 10000 个资源；容量满时拒绝新增，不提前淘汰仍有效的防重记录。投递租约两分钟；Telegram 限流冷却按返回值限制在一秒至一小时。回执只保存哈希、随机领取令牌及状态/时间，不保存原始订单号、用户 ID、金额、币种或通知正文；哈希不等于敏感数据的加密。
- 默认内存模式仅保证当前进程内去重，重启会丢失。Redis 数据删除、回滚、故障切换丢写、命名空间变化、七天到期或回退到不识别回执的旧 Bot 后，都可能重新通知。必须避免绕过保护。
- **不承诺消息恰好一次。** Telegram 已接收但 HTTP 响应丢失、或发送成功但最终回执未能保存时，无法判定实际送达。未决租约过期后，上游重试可能再次发送；故障测试明确断言了这一可能性。Bot 没有可靠永久消息 outbox，上游重试耗尽也需人工排查。
- 回调仅发送通知，绝不重放支付、充值或提现请求；余额、订单状态、账务流水和提供方回调幂等性由 Dujiao-Next 负责。通知成功不等同于账务对账成功。管理员摘要仍是独立的有界尽力通知。

## 隔离与本地结果

测试不读取 `.env`、真实 Token 或商店密钥；随机创建内部 Docker 网络、容器、凭证和数据库，不连接演示栈、不公开服务端口。宿主测试经 loopback HTTP → `docker exec nc` 透明隧道访问；官方后端、Bot、队列和协议 peer 都在无外网路由的网络中。`Dockerfile.e2e`/`cmd/e2e-peer` 是测试设施，不进入正式 Bot 镜像或发布包。

清理前核对随机 owner 标签，只移除本次容器、网络和测试镜像。合成配置/SQLite/日志留在打印出的私有临时目录，失败时也保留 peer 状态及 PostgreSQL 数据卷，供本机排查；成功的 PostgreSQL 测试卷由测试清理。不要上传整个临时目录或对现有业务卷执行清理。
