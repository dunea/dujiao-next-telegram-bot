# v1.0 开发验收：大批量 TXT 交付

仍为 `1.0.0-dev`，不发布正式版本。支付与库存由 Dujiao-Next 管理，Bot 的“领取”只读取交付结果并发送附件，不再次购买、扣款、分配卡密或修改履约状态。

## 内容和隔离

- 订单页只展示摘要与下载按钮，不展示卡密原文。仅接受 `chat.id == from.id > 0` 的私聊；每次下载/重发均以当前 Telegram 用户 ID 调用带 `channel_user_id` 的 Channel API 查订单，不接受回调传入的买家 ID。不存在或他人订单不发送文件。
- 交付完成通知亦可一键下载；通知只是入口，不额外上传文件。通知与订单详情共用同一防重记录，重启后点旧通知或切换入口不会绕过保护；新状态（例如退款）仍在每次点击时核验。
- UTF-8 TXT 收录主订单及全部子订单的内容、主订单/商品/子订单使用说明；字符串保留原始空格、换行和特殊字符，不 HTML 转义。结构化内容用格式化 JSON。只有“主订单与唯一子订单完全相同”的镜像内容省略主订单副本，不对不同子订单中的相同卡密去重。
- 仅允许 `paid`、`processing`、`completed`、`delivered`、`partially_delivered` 且已有交付内容的订单；兼容官方人工履约返回 `delivered` 的分支。未付款、取消、退款、未知状态不开放下载。部分交付时文件包含当前商店已返回的内容；更新后可主动重发获取新版，不承诺未交付商品已经完成。
- TXT 上限 4 MiB，与现有商店响应预算一致。无法完整生成时明确失败，不发送截断文件。文件名仅含数字订单 ID，内容在内存生成后通过 SDK multipart 上传，不写本地明文文件、不使用公网下载 URL、不缓存 `file_id`。
- 文件允许买家下载；未启用会影响保存/转发的 `protect_content`，该参数的含义见 [Telegram 官方 sendDocument 文档](https://core.telegram.org/bots/api#senddocument)。用户主动分享、截图或转发不受 Bot 控制；这里的隔离是服务端授权与收件人隔离，不是 DRM。

## 防重复与故障

Redis 使用独立 `delivery:v1` 命名空间，不改变既有提现、购买、回调或群发格式。键为用户/订单摘要；值只有版本、内容 SHA-256、随机领取令牌、状态、消息 ID、冷却时间及过期时间。七天 TTL、最多 10000 条有效记录，容量满时拒绝新领取，不驱逐现有防重记录。内存模式有同样的并发保护，但不提供重启持久性。

1. 先以单次 CAS 持久记录 `posting`，确认写入成功才上传。CAS 冲突、连接错误、写入响应丢失、epoch 丢失、损坏数据和容量不足均不授权上传，不自动重放更新闭包。
2. 同一用户/订单无论内容是否变化，已有记录都不会通过普通点击重复上传。成功记录消息 ID；一分钟后普通点击仅展示第二次确认按钮，令牌绑定上一尝试。确认后更换令牌，旧按钮失效。
3. 上传最多一次、最多 60 秒。超时、5xx、403、响应丢失、进程中断或完成回执写入失败均保留未确认状态，不能凭两分钟过期自动重领；两分钟只是允许用户核对聊天后主动确认重发的最早时间。
4. 明确的 429 说明 Telegram 拒绝此次上传，按 `retry_after` 冷却 1–3600 秒后允许再点击领取。不进行后台补投。
5. 完成回执使用独立于已取消请求的短超时保存。日志不记录卡密、文件、错误正文、Token 或 Telegram 上传 URL；审计 `delivery.txt` 只包含用户/订单数字 ID、事件与结果。

这是有界防重复发送，不是永久的一次性消费锁。七天到期、显式确认重发、Redis 数据丢失后重新初始化环境，均不构成 exactly-once 保证。Redis 应启用持久化和 `noeviction`，备份与恢复需保留此命名空间及 epoch；不得用清空 Redis 解除领取保护。

## 自动验收

```sh
make verify
make telegram-e2e
```

- 离线测试：5000 条含特殊字符的原文及末行、全部子订单/说明、镜像与重复卡密、4 MiB 边界、状态过滤、私聊/归属校验、并发点击、重发令牌失效、SDK 429/500/403/已接收但响应丢失、领取/完成存储故障。
- Redis 测试：跨客户端单次领取、导航/进程重建保留状态、容量/损坏/epoch/CAS 冲突及响应丢失。现有真实 Redis AOF 两阶段测试加入 `sent` / `posting` / `retry` 三种 TXT 状态，重启后逐一核对。
- 双数据库实栈：使用固定官方 Dujiao-Next v1.5.0，正常后台 API 分五批导入 2500 条合成卡密；通过实际 Telegram 按钮输入 2500、下单、模拟在线付款、官方自动履约。peer 只保存附件长度/文件名/SHA-256，逐字节摘要与官方完整交付比对；重复点击、Bot 重启后仍只有一个附件，库存与钱包不发生额外变化。
- 原小批量自动交付与人工交付 E2E 同步改用真实 SDK 附件路径。CI 仅上传脱敏输出，不上传卡密、数据库、peer 状态或凭证。

本地 Docker Desktop 真人测试仍使用已获授权的独立测试商店；真实 Telegram、内部模拟支付，无真实资金。通过协议 peer 的文件完整性测试不等于已验证所有真实 Telegram 客户端的下载体验，也不等于公网真实支付验收。
