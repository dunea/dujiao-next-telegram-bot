# v1.0 发布准备与门槛

当前 `1.0.0-dev` 仅准备候选包，**尚未正式发布 v1.0.0**。稳定版仍为 v0.4.0；不移动旧标签、不覆盖旧发布附件。自动验收范围与剩余人工项见[整体验收](acceptance-v1.0.md)。

## 候选包生成与复核

```sh
make verify
make acceptance
make real-upstream-test
make telegram-e2e
make soak-test
# 提交已验证源码，确认工作区干净后：
make release-candidate
```

候选包写入全新 `dist/candidates/1.0.0-dev-<完整提交号>/`，已存在则拒绝覆盖；不改变主程序版本号、不创建标签或 GitHub Release。Linux/macOS 各有 amd64、arm64 包，包含 Bot、只读 compatcheck、构建信息、全部公开文档和第三方许可证。不得上传打包工作目录中的依赖本地路径清单、解包目录或任何私有配置。

对待发布目录执行 `go run ./cmd/releasecheck -dir <目录>`，验证四个 SHA-256、归档白名单/路径/大小、ELF/Mach-O 架构、Go 工具链、干净源码提交及静态构建标记、许可证和相对文档链接。检查器不解压执行文件、不读取部署凭证、不联网。CI 另运行 Linux amd64 包的离线版本、安装帮助和兼容矩阵；本地可运行本机架构对应命令。交叉编译/头部校验不等于所有操作系统都通过原生运行。

下载后将文件摘要与同批 `checksums.txt` 对照，来源提交与 `release-manifest.json`、二进制构建信息保持一致。SHA-256 是完整性校验，不是代码签名、独立可信来源或供应链证明；候选构建不是已发布多架构容器镜像。

## 正式发布前六道门

1. 最终提交的格式/竞态、持久化/升级、真实双数据库 E2E、持续负载、Docker、四平台包校验全部通过；只认同一提交，不使用旧 CI 代替。
2. 人工 Telegram 验收：移动端和桌面端分别完成购买、付款恢复/取消、充值、通知查单/TXT、编号查单和客服。检查按钮数量、下一步提示、返回位置和错误恢复；不需要连续点击加号。
3. 商家选定支付提供方的沙箱闭环：签名、金额/手续费、重复/迟到回调、取消/超时后到账处理、充值账本和交付。仅模拟 Epay 通过不勾选该项；不使用真实资金压测。
4. 生产部署演练：独立测试 Bot、单实例轮询、可靠 Redis AOF/无驱逐、稳定加密密钥、健康/告警、审计轮转、备份恢复和兼容回滚。关键资金操作不得回退空内存保护。
5. 人工核对已知边界与未决问题；最大容量、长时间运行和历史 503 的证据不足明确披露。商家售后按账本及身份核实，订单号不构成退款授权；不自动退款/打款。
6. 得到正式发布授权后，单独将版本改为 `1.0.0`、完善最终变更及验收记录，重新验证最终提交。执行稳定版 `make release`，再创建固定标签与公开 Release，上传四包、校验清单及来源清单；不把开发候选包改名冒充正式包。

当前准备工作不会自动执行第六项，不发布或覆盖任何正式版本。

## 升级与回滚约束

完整安装、配置比较、备份和故障处置见[运维指南](operations-v1.md)。升级前核对未决支付/提现/群发和商店账本，保存当前代码/镜像标识及一致性备份；保持 Compose 项目名、数据卷、商店地址、Channel Key 和会话加密密钥稳定。

仅更新 Bot，不重建存有数据的商店、Redis 或模拟支付网关；不执行 `down -v`。先运行离线 `setup check` 和只读兼容检查，再核对版本、健康、签名回调、历史订单、TXT/资金保护和管理员权限。健康 200 不等于真实支付闭环已通过。

回滚优先切回能读取并执行当前保护语义的已知兼容代码/镜像，保留当前业务状态。旧版“能读”不代表它认识新保护；v0.4.0 不具备开发版结账/TXT 的全部语义，不据存储兼容测试直接降级继续资金操作。不要恢复旧 Redis 快照以回滚程序，否则可能丢失退订、防重和已发操作保护。无法确认时停止写操作并人工核账，禁止清库、换密钥或重放结果不明请求。

## 真人验收记录模板

由测试者记录：提交/镜像、上游版本、客户端版本、测试时间、匿名订单引用、预期/实际、通过/失败及脱敏截图。不要公开 Token、Channel Secret、完整邮箱/收款资料、支付凭证或卡密；失败先保留现场再修复。客服预填只准备草稿，需用户核对收件人并主动发送。
