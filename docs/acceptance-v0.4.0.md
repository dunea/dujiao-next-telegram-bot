## Docker 整体验收

使用固定项目 `dujiao-bot-integration` 和 `compose.test.yml` 执行 `make acceptance`，生产 Bot 与 Mock 镜像构建成功：

- 容器内版本 `0.4.0`，健康 200。
- AOF 种子写入、重启 Redis、恢复验证通过：语言、提现草稿/保护、耗尽限流额度、公告订阅/草稿/领取进度和冷却保留；群发任务保持暂停。
- 停止测试 Redis 时健康为 503，恢复后为 200。
- 2000 次健康请求、并发 50：失败 0。
- 1000 次分散用户签名回调、并发 25：失败 0、非预期超限 0。
- 500 次单用户签名回调突发、并发 25：390 次预期 429，均有 Retry-After，失败 0。
- 仅重启 Bot 后审计文件原 inode 保留，内容非空、权限仍为 0600；容器与卷保留。

上述请求是本机隔离吞吐检查，不是 Telegram、商家服务器或真实支付渠道的吞吐保证。重复压测可能因仍在恢复中的额度而改变 429 数量；测试断言只要求预期突发中确实出现超限且没有异常失败。

## 发布门槛与边界

正式标签指向同一发布提交，发布前核对该提交的 Go/Docker CI 成功。下载包为 Linux/macOS 的 amd64/arm64 静态 Go 交叉构建，附构建提交信息及 SHA-256；具体远端 CI、发布附件与标签以 GitHub 对应页面为准，不把交叉编译等同于四平台原生运行验收。

真实演示栈仅升级 Bot 容器，保留原管理员白名单、Redis/审计卷及商店进程。程序/容器版本和健康检查通过不代表已代用户完成真实 Telegram 购物、群发或商家支付验收。

生产应使用可靠 Redis、稳定加密密钥和单实例 Telegram 长轮询。管理员通知仍是内存尽力队列；提现无服务端幂等键，公告对不确定结果保守暂停，不提供数据删除/回滚后的全局恰好一次保证。升级与回滚不得通过清空 Redis、换密钥或恢复旧游标绕过保护。操作说明见 [RELEASE.md](../RELEASE.md)。
